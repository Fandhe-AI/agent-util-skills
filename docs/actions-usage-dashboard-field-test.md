### 請求画面との照合

2026-10 の含有枠を、請求画面（Settings → Billing → Actions）の使用量と比べた。

- summarize.py は「消費 X 分以上（下限。区分不明あり）」と出したが、その値が請求画面の使用量を約 0.9% 上回った
- API を取り直しても同じ値だったため、請求画面の反映遅れではない
- 原因の候補は次の 3 つで、どれが効いているかは未確認。Issue #209
  1. `--assume-current-visibility` による公開範囲の誤分類
  2. 換算式「定価 ÷ Linux 単価」と請求画面の換算の違い（macOS の倍率・安い SKU）
  3. 端数処理
- summarize の表示が下限と言えるのは、区分不明だけが差の原因のときに限る

#### 表示の見直し（#209）

- 実測は `--assume-current-visibility` 付きで、included 行があり unknown が 1 行あった。この場合の quota は現在の公開範囲と換算式に依存する値で、上振れも下振れもあるため、下限ではなく概算である。旧実装は unknown > 0 だけで「下限」と出していたため、値が請求画面を上回る結果が下限の主張と矛盾した
- 下限と言えるのは、quota が構造上 0 の既定モード（非有料分がすべて unknown）で unknown 分だけ少なく数える場合に限る。それ以外の分類済みの値は「約 X 分（概算）」と表示する。規則は references/data-sources.md「含有枠の消費の確度」
- fetch_billing.py の出力に `assume_current_visibility` を記録し、summarize が方式を推測せず読めるようにした
- ダッシュボードの雛形も同じ規則にした。`assume_current_visibility` は build_dashboard が billing_meta の行で渡し、分類済みかどうかは summarize と同じく文書全体で判定する。概算のときは区分不明の有無にかかわらず枠消費の値に「（概算）」を付け（残量は「約」付き）、タイル・表・凡例・ツールチップ・グラフ下の注記のどれにも「以上」を出さない。実機の画面での確認は 2026-10-28 に行い、期待どおりだった（「既存ダッシュボードの移行」節）
- 公式の Actions 課金ページ（確認日 2026-10-28）は SKU ごとの分単価を載せるが、含有分の消費の倍率は書いていない。換算式が請求画面と一致するかは未確認のままである
- 3 要因（公開範囲の誤分類・換算の違い・端数処理）の寄与は、この時点では未検証だった。次の「差の切り分け（#221）」で切り分けた

## check 文書の仕様確認（#206）

確認日は 2026-10-28。出典は Dashboard 型の参照文書 `artifact-type/reference/features.md` の「The check document」と「The runs document」で、Artifact の `read` に `path` を付けて読んだ。

- 書き手と時機: 開いているダッシュボードが、ページを書き込んだ後に書く。閲覧者がページを開いただけでは書かれない
- 状態値: `checking`（読み込み中。最大 5 回まで読み直す）と `failed`（`page` に `kind` / `name` / `what` / `count` など）の 2 つだけ。成功を表す値は無い
- 文書が無いとき: まだ始まっていない、ページが合格した、ダッシュボードが閉じている、データの読み込みが遅れた、チェックが無効、のどれかを表す。区別できない
- 修正して書き直した後も `at` が変わらなければ、もう 1 回読み、それでも変わらなければダッシュボードは閉じている

実測との照合:

- 既定の更新 2 回: ページを書き込まないため、文書が無いのは仕様どおり
- 作成: ダッシュボードが開いていたか、合格したかを区別できない
- 持ち主がページを開いた後も無かった点: 開くだけでは書かれないという仕様と一致する

結論として、当時の完了条件（成功状態の文書を要求）は型が一度も書かない値を求めており、手順どおりでは必ず未完了になっていた。SKILL.md の完了条件を、check を「失敗を検出する否定ゲート」とし、文書なしは検証未確認として未完了を維持し、目視の返答では完了にしない形に改めた。ページを書き込まない既定の更新では check の代わりに dataset 文書の読み戻し（読める・source と updated が一致・版が進んだ）を条件にする。

新しい条件で当時の実行を文書上で判定し直すと、作成は「未完了（check 未確認・文書なし）」、更新 2 回は読み戻し確認を行っていないため「未完了（公開後の読み戻し未確認）」となる。再実行はしていない。
